# PV.VaultSchema - Markdown-vault entity schema: directories, ID allocation, discovery

> **Trigger:** When you need to know where an entity lives, how to allocate its ID, how to find it, or when the vault schema changes (a new entity kind, directory, or carrier).

```episteme id="PV.VaultSchema" context="ProjectVault"
Grounding (FPF):
  builds_on: A.7, C.33, C.2.1, E.4.DPF
  coordinates_with: F.14, F.18, C.32.ADR

UseThisWhen:
  laying out or maintaining the vault entity model: which entities exist, where they live, how IDs are allocated, how entities are discovered

Result:
  the entity model definitive: top-level structure, entity kinds, ID allocation, discovery, CLI

Solution:
  TopLevelStructure:
    canonical carrier project-vault/; two channel dirs at repo root: inbox/ (PV.Inbox), outbox/ (PV.Outbox)
    project-vault/ layout:
      decisions/ — atomic decision cards (DEC-NNNN.md), the single state entity
      tracks/ — operational tracks (TRK-NNNN.md) + auto _index.md
      work/ — work records (WRK-YYYY-MM-DD-hhmmss.md) + auto _index.md
      artifacts/ — artifacts bound to tracks (YYYY-MM-DD-slug.md)
      sources/ — raw source materials (flat captures)
      scripts/ — vault.py (ID + indexes + integrity check), export_dec.py
  Entities:
    atomic .md = YAML frontmatter (id, status, updated, sources) + Markdown body
    closed entities stay in place with a frontmatter status (no archive/ mirror)
    outbox/ message is the exception: one file = one message, frontmatter created/addressee/source_project/source_context/status (pending → sent), no monotonic ID, no _index.md (PV.Outbox)
    inbox/ holds raw incoming sources, cleared after processing (PV.Inbox)
    service track: still tracks/TRK-NNNN.md in the same flat TRK namespace, kind: service frontmatter, the WRK container for repeating maintenance (PV.Track T.5)
  Discovery (no manual indexes):
    semantic: SocratiCode codebase_search over project-vault/
    exact: grep -l "^status: open" project-vault/decisions/ (open registry); grep -l "^status: proposed" project-vault/decisions/ (formed-but-unapproved)
    full list: Get-ChildItem / ls
    indexes: only work/_index.md and tracks/_index.md, auto-generated by vault.py (after each WRK — vault.py all; after a track status change — vault.py tracks)
  IDAllocation:
    new IDs (DEC/TRK) only via python project-vault/scripts/vault.py next-id (or next-id TRK)
    monotonic, not reused; closing does not free the number
    integrity via python project-vault/scripts/vault.py check (no duplicates, no ID desync)
  CLI:
    python project-vault/scripts/vault.py <command> [--path <abs-path-to-project-vault>]
    --path required when invoked not from the repository root

Stop:
  every entity kind has a home; discovery, ID, and integrity questions are answerable without hand-maintained indexes

Checks:
  every entity is an atomic file in its kind directory
  no manual _index.md in entity directories; only work/_index.md and tracks/_index.md are auto-generated
  IDs issued only via vault.py next-id; monotonic, not reused
  discovery reachable via grep / SocratiCode / ls
  closed entities stay in place with a status, without an archive/ mirror
  vault.py check passes (no duplicates, no ID desync)

Antipatterns:
  manual _index.md in an entity directory → remove; discovery via grep/SocratiCode
  ID assigned via ls → always vault.py next-id
  closed entity moved to archive/ → leave in place, set a status
  duplicate copy of the schema in several places → one canonical body, the rest refer to it

Continues:
  PV.Init (scaffold copy), PV.Migration (retire kinds/directories), PV.StateUpdate/PV.Track (entity use in procedures)

Reopen:
  A.7 / C.33 / F.14 revision, or a search-tool change
