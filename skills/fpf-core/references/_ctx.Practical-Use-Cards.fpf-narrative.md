```episteme id="Practical-Use-Cards" context="FPF-Core.PracticalUse"
UsePrinciple:
 start from current project question, not ordinal route through FPF
 the fifteen semantic keys are stable identifiers, not steps
 when several cards seem plausible → compare situations, first-result differences, stop/return conditions in conversation
 then inspect direct pattern's Problem-frame, Problem, Forces, Solution, Consequences, ordinary boundary
 materialize comparison or candidate records only when a named receiving use relies on them
ConditionalTemplateSemantics:
 the conditional template list is one ordinary walkthrough
 inspect only the branch whose stated condition is current → apply that direct pattern's Solution → obtain its exact result → stop/return at card boundary
 it is NOT a DemonstrativeUnfoldingSlice@Context — card asserts no single wider constraint-governed structure over all alternatives
 the list is not a project order, nor a claim that all branches execute
DomainNeutrality:
 cards are domain-neutral
 first useful result may be physical/clinical state, capability, episteme, relation, dated U.Work, or another exact subject-governed value
 a generated note/measurement/dashboard/plan does NOT stand for machining, treatment, organizational change, learning, or another downstream result

ARCHITECTURE:
 intent: shape architecture from problem pressure
 situation: architecture-relevant problem pressure and competing characteristics present; project must carry them toward candidate/selected/expected/actual structures
 question: which architecturing flow or description-use result is needed first?
 obstacle: candidate structures, architecture characteristics, or the pressure↔structure relation not yet reviewable
 templateA: C.32.P2S Solution → ProblemToStructureArchitecturingFlowCard@Project — when connected problem-to-structure flow is current; local basis adds architecture-relevant pressure refs and current architecture-characteristic refs
 templateB: C.30.AD Solution → ArchitectureDescriptionUseCard@Project — when existing architecture description/view is the object used and its admissible-use boundary is current
 stop: when selected first card makes receiving architecture work reviewable
 return: when problem pressure, EntityOfConcern, characteristics, description edition, or actual-structure feedback changes
 wrong-turn: diagram-as-architecture claim → C.30 and C.33
 stronger-neighbors: C.32 synthesis, C.32.PAD decision, A.15 work, E.23 improvement, G.11 currentness — per next claim
 public-coarsening: "Architecture working card" restores to one of the two exact project cards; does not denote architecture itself

WORKING-DOCUMENTS:
 intent: create a document another participant can use
 situation: participant asks for regulation/procedure/plan/interface description/permission text/evidence note/gate record/publication/AI tool-use plan
 question: which use is current — preserve meaning, prepare enactment, support reliance/gate, or publish governed content? reader inspects only the selected branch
 branchA.preserve-meaning:
  A.6 Solution → Claim Register (or small claim set classified L/A/D/E) when one text mixes definitions, admissibility, commitments, evidence claims
  A.3.2 Solution → U.MethodDescription when result describes a reusable semantic way-of-doing under conditions
  A.2.8 Solution → U.Commitment when accountable subject's obligation/permission/prohibition + scope + validity window + referents is the actual result
  A.6.RSIR when "interface" still hides which claim (signature/slot/module-interface/functional-port/protocol/service-relation/publication) — used ONLY to select direct governing pattern, retain reduced-use source label, or return a blocker; RSIR does not produce downstream interface result; once direct claim recovered use its pattern; A.6.M only for a recovered module-interface relation
 branchB.prepare-enactment:
  A.15.2 Solution → U.WorkPlan when stating intended dated work, PlanItems, assignments, resources, windows, sequencing constraints is current
  C.24 Solution → CallPlan | CheckpointReturn when tool-call enactment is current — CallPlan after routes+budgeted execution fixed enough, CheckpointReturn while bounded probing remains the honest result
  A.15.5 Solution → WorkEntryReadiness@Context only when intended work already exists and readiness to cross its work boundary is current
 branchC.support-reliance-or-gate:
  A.10 Solution → claim-bound evidence-provenance graph relation when named receiving use relies on recovering basis for one claim/effect through evidence-producing/interpreting work, trace, time window, bounded use
  B.3 Solution → Assurance(H, C | K, S) or explicit no-assurance-claim disposition when text is expected to carry a named assurance claim, not merely point to evidence
  A.21 Solution → OperationalGate(profile) use with GateProfile, effective GateCheckRefs, aggregated CV status, GateDecision, DecisionLogRef when exposing an actual gate decision is current; a readable checklist is not that decision
 branchD.publish-governed:
  E.17 Solution → source-pinned publication face when readable/exchangeable/citable publication of an already governed episteme or relation is current without changing the underlying claim
 stop: when selected branch yields the exact result its receiving use needs
 return: when the expected use changes
 constraint: one document may cite results from several branches, but page proximity does not merge their kinds nor transfer claims to a different governing pattern; RSIR stops at pattern selection / reduced-use labeling / blocker and never certifies an interface relation exists
 public-coarsening: "Working document" is only a situation label; expansion restores selected branch, direct pattern, exact result, receiving use

OPTION-COMPARISON:
 intent: compare alternatives and select the current result kind
 situation: several possibilities present; current need may be to define comparison, retain diversity, govern a live pool, publish a selected set, or make one local choice
 question: which of those relations is current?
 templateA: A.19.ECS Solution → EvaluationCharacteristicSpaceSpec — when coordinates/scales/evidence-rules/protected-trade-offs inadequate for comparison
 templateB: C.18 Solution → ExplorationArchiveRecord@Context | FrontRecord@Context — archive when later use relies on retained variants + lineage/diversity; front when later use relies on inspectable non-dominance + comparator basis
 templateC: C.19 Solution → PoolPolicyResult — when a still-live pool needs one explicit widen / keep-frontier / narrow-to-subset / sunset-line treatment + change trigger
 templateD: G.5 Solution → Shortlist | RankedShortlist | SpecialistHandoff | abstain-or-escalation outcome — when selector-facing publication of a set or narrowed handoff is current; ranked only when order materially belongs to published result
 templateE: C.11 Solution → ChoiceResult — when an OptionSet and comparison basis exist and one local choose/reject/probe/reroute result is current
 stop: at the result answering the current option question
 return: when candidate membership, archive policy, dominance basis, pool policy, selector publication, comparison basis, preference order, or probe value changes
 constraint: archive ≠ live pool; narrowing a pool ≠ publishing a shortlist; shortlist ≠ local choice
 public-coarsening: "Option comparison" restores to evaluation-spec / archive / front / pool-policy result / selected-set publication / local choice under its exact condition

PROBLEM-SHAPING:
 intent: turn early pressure into an honest problem-side result
 situation: something matters, but may still be an early cue, possible inquiry routes, an abductive question, or a problem ready for acceptance
 question: how far has articulation actually progressed?
 templateA: A.16.1 Solution → U.PreArticulationCuePack — when a cue nucleus + witness/anchor should be preserved before a route/problem claim is stable
 templateB: B.4.1 Solution → RoutedCueSet — when cue content is stable enough to publish route plurality or one selected route with explicit rationale, no later endpoint yet warranted
 templateC: B.5.2.0 Solution → U.AbductivePrompt — when prompt species, open question, scope, cue provenance stable enough to seed abductive search
 templateD: C.22.2 Solution → ProblemCard@Context — when affected EntityOfConcern, constraints, unresolved relations, distinctions-to-preserve, acceptance basis can be stated without smuggling in a selected solution
 conditional-continuation: C.22 Solution → TaskSignature when accepted problem-side record must become usable by later eligibility/acceptance/method-family selection; TaskSignature types only current problem traits + receiving use; does NOT select a method, issue a selector verdict, plan work, or prove work occurred
 stop: at the earliest result that is both truthful and useful
 return: when cue anchor, route rationale, prompt contrast, affected EntityOfConcern, constraint, or acceptance basis changes
 discipline: do not force a cue into a ProblemCard merely to make work look started
 public-coarsening: "Problem shaping" restores to exact cue pack / routed cue set / abductive prompt / accepted ProblemCard under its articulation condition

IMPROVEMENT:
 intent: define evaluation before repeating improvement
 situation: a named object version should improve, but evaluation purpose / quality family / scales / proposal effect / repeated-loop need may be unsettled
 question: which prerequisite for improvement is missing now?
 templateA: E.22 Solution → QualityEvaluationQuestionFrame — first, when evaluation purpose / floor-or-aim / protected-trade-offs / expected-evidence-basis / expected-result-form not yet agreed
 templateB: C.25 Solution → Q-Bundle — when a composite engineering quality family needs bearer, components, measures, scope, mechanisms, status, evidence relation
 templateC: A.19.ECS Solution → EvaluationCharacteristicSpaceSpec — when object-specific coordinates/scales/comparators/evidence-rules do not yet exist
 templateD: E.23 Solution → QualityImprovementLoopRecord — only when object version + evaluation basis exist and repeated proposal, change, coordinate-qualified re-evaluation, loop decision are current
 stop: at the smallest missing frame / Q-Bundle / evaluation-spec / completed local loop record
 return: when object version, evaluation purpose, Q components, scale, comparison set, evidence basis, expected result, or protected trade-offs change
 discipline: "repeat until better" is not a loop method until better is evaluable on declared coordinates
 public-coarsening: "Improvement frame" restores to the exact result under its prerequisite condition

COSTLY-ACTION:
 intent: prepare an expensive or hard-to-reverse action
 situation: proposed action is expensive/externally-committing/safety-relevant/hard-to-reverse
 question: which unresolved uncertainty or governing relation currently prevents responsible commitment, gate use, intended work, or performed work?
 templateA: A.10 Solution → claim-bound evidence-provenance graph relation — when support basis for one claim/effect not recoverable
 templateB: B.3 Solution → Assurance(H, C | K, S) or explicit no-assurance-claim disposition — when action depends on a named assurance claim + its limitations + decay condition
 templateC: A.20 Solution → path-slice-local CV result with step, CV class, CV.Status, witness-or-refusal — when constraint validity is the current question; this result does not itself pass a gate
 templateD: A.21 Solution → OperationalGate(profile) use with GateProfile, GateCheckRefs, aggregated CV status, GateDecision, DecisionLogRef — when a real gate decision is current
 templateE: C.28 Solution → CausalUseTriageRecord — when expected effects/intervention/counterfactual/policy claims carry the action rationale and their supported-rung boundary is current
 templateF: C.11 Solution → ChoiceResult — when several actions remain live and current result is choose/reject/probe/reroute
 templateG: A.15.5 Solution → WorkEntryReadiness@Context — only after intended work exists and readiness to enter its work boundary is the current relation
 stop: at the first result that decides the present uncertainty; do not force every costly action through all templates
 return: when claim, evidence path, assurance context, constraint definition, gate profile, causal-use basis, option set, intended work, resource state, cost, or reversibility changes
 discipline: planning/readiness does not authorize or perform work; a gate display does not replace GateDecision
 public-coarsening: "Costly action" restores to exact evidence/assurance/constraint-validity/gate/causal-use/choice/readiness result under its selection condition

TIME:
 intent: use timing and currentness claims responsibly
 situation: a claim about rate/rhythm/delay/effort/inertia/recovery/currentness/validity-window is being used for action
 question: is temporal-claim adequacy or source-currentness orchestration current?
 obstacle: snapshot used as trend, trend used as control law, or old edition used as current
 templateA: C.27 Solution → Dyn2TemporalClaimAdequacyCard — when a local temporal claim changes supported use
 templateB: G.11 Solution → RefreshCurrentnessLine@Context — when freshness/edition/telemetry/decay/currentness is the live claim
 stop: at the smallest supported temporal card or currentness line
 return: when window, bearer, evidence relation, model assumption, source edition, or telemetry changes
 wrong-turn: downgrade unsupported rate/currentness claims
 stronger-neighbors: C.16 measurement, C.28 causal use, A.15 work, direct source/publication governing patterns
 public-coarsening: "Time check" restores to the C.27 card or G.11 line

CAUSAL-USE:
 intent: bound causal language before using it for action
 situation: causal/intervention/effect/policy/counterfactual language is being used to support a decision or action
 question: what causal-use rung and support basis are actually available?
 obstacle: association, intervention, and counterfactual claims treated as interchangeable
 templateA: C.28 Solution → CausalUseTriageRecord — initial template; local basis adds live causal wording, target use, candidate rung, comparator/counterfactual, support-basis refs
 stop: at the triage record when it honestly bounds supported and unsupported use
 return: when intervention, comparator, target population, evidence, or causal-use purpose changes
 wrong-turn: downgrade causal laundering to the supported claim
 stronger-neighbors: CausalUseEvidenceDesignRecord / CausalUseSupportVerdict inside C.28, C.11 for choice, direct evidence/work patterns
 public-coarsening: "Causal check" restores to CausalUseTriageRecord

DESCRIPTION-USE:
 intent: create or use a description without losing its subject
 situation: a description/view/dashboard/explanation/model/report/publication is to be created, compared, transformed, or relied on
 question: which unresolved EntityOfConcern / viewpoint / representation change / lost structure / source set / architecture use blocks the current use?
 templateA: E.17.0 Solution → DescriptionContext — generic describing case; name EntityOfConcernRef, BoundedContextRef, ViewpointRef, resulting view/view-family, any correspondence relation needed for current comparison
 templateB: A.6.3.RT Solution → RepresentationSchemeTransitionRelation@Context — when same EntityOfConcern is re-represented and a named receiving use relies on recovering source representation, receiving representation, preserved claim/commitment, source-relation chain, scheme delta, loss/recoverability, admissible use, non-admissible downstream use; relation records the concrete case; RepresentationSchemeTransition remains the method-pattern name
 templateC: C.33 Solution → StructuralInformationAdequacyNote@Context — when question concerns what structure a description/view captured, lost, hid, and which wider source structure receives return for the declared architecture use
 templateD: E.17.ID.CR Solution → ComparativeReviewUnit — only for bounded comparison over already-available source epistemes/publications; not the generic description result
 templateE: C.30.AD Solution → ArchitectureDescriptionUseCard@Project — when subject is specifically an architecture description/view and its admissible architecture-use boundary is current
 stop: at the smallest result answering the current description-use question
 return: when EntityOfConcern, context, viewpoint, representation scheme, captured structure, source edition, comparison basis, or intended use changes
 discipline: a publication carrier does not become its subject; a readable view does not become evidence/assurance/permission/decision/architecture/work without the corresponding governed relation
 public-coarsening: "Description use" restores to DescriptionContext / RepresentationSchemeTransitionRelation@Context / StructuralInformationAdequacyNote@Context / ComparativeReviewUnit / ArchitectureDescriptionUseCard@Project under the stated condition

NAMING:
 intent: name a governed value for its readers
 situation: a governed value needs a stable Tech or Plain label across a bounded context
 question: which name lets readers recover the value without changing its kind or scope?
 obstacle: candidate labels carry conflicting senses, hidden kinds, or misleading morphology
 templateA: F.18 Solution → NameCard — local basis adds governed value, governing pattern, bounded context, candidate set, rejected candidates, rationale, bridges, lineage, refresh condition
 stop: at a complete NameCard when no public term publication is current
 return: when governed value, context, candidate evidence, reader interpretation, or bridge changes
 wrong-turn: restore the governed value before selecting a label
 stronger-neighbor: F.17 only when actual term-row publication is current
 public-coarsening: "Naming card" restores to NameCard

WORDING:
 intent: repair wording without changing the kind by accident
 situation: a sentence sounds fluent but hides which object/relation/slot/use-position/claim-kind is active
 question: what was the pre-repair kind and which invariant is preserved after rewriting?
 obstacle: a trigger word replaced while ontology, admissible use, or scope drifted
 templateA: E.10 Solution → KindRestorationCheck — local basis adds exact span, pre-repair kind, relation, position, use, scope, post-repair settlement, governing-pattern ref, disposition
 stop: when repaired wording preserves or explicitly changes the kind by accepted decision and remains understandable under MG-DA
 return: when the sentence's EntityOfConcern, use, or scope changes
 wrong-turn: reject lexical substitution without semantic check
 stronger-neighbors: F.19 for phrase-level prose repair, F.18 for durable naming, direct domain pattern for ontology repair
 public-coarsening: "Wording repair" restores to KindRestorationCheck plus the changed sentence

MATHEMATICAL-MODELING:
 intent: use a mathematical lens when it changes the next action
 situation: a project question may benefit from a mathematical object/lens, but next action and lost structure not yet clear
 question: can one cheap lens result change the next admissible action?
 obstacle: a metaphor (graph-like, field-like, optimization-like) treated as ontology or evidence
 templateA: C.29 Solution → MathLensUse.LensCandidateNote — when no adequate mathematical object has yet been named
 templateB: C.29 Solution → MathLensUse.OneLine — when candidate object, mapping, preserved structure, lost structure, payoff, next action, rival/fallback, stop condition can be stated
 stop: at NoMathLensUseNeededNote, candidate note, or one-line result per C.29
 return: when EntityOfConcern, mapping, observation, preserved structure, or intended use changes
 wrong-turn: remove lens-as-world or lens-as-evidence overread
 stronger-neighbors: C.29 MiniCard/FullCard, C.16 measurement, C.28 causal use, C.30 architecture use
 public-coarsening: "Mathematical-modeling note" restores to the selected MathLensUse.* output

SOTA-PORTFOLIO:
 intent: build a plural current field of options and sources
 situation: a project needs the current plural field of methods/theories/technologies/design-options rather than one favored source
 question: first, what source and tradition synthesis is adequate; then, which stewardship relation is current for the resulting candidates?
 templateA: G.2 Solution → SoTA Synthesis Pack@CG-Frame — when immediate need is a reconstructible SoTA_Set@CG-Frame + SoTAPaletteDescription with rival traditions, claim rows, evidence anchors, crossings, source-use boundaries
 conditional-walkthrough:
  C.18 → ExplorationArchiveRecord@Context if later use relies on retained generated/harvested variants
  C.18 → FrontRecord@Context if later use relies on exposed non-dominated variants
  C.19 → PoolPolicyResult if a still-live pool needs treatment
  G.5 → Shortlist | RankedShortlist | another declared selector outcome if a selector-facing set is to be published
  these are conditional continuations, not synonyms or serial stages
 stop: at the pack when downstream stewardship is not current
 return: when scope, traditions, source editions, evidence anchors, or harvest policy changes
 discipline: archive, front, live pool, selected set keep different membership/policy/publication meanings; no prose summary may collapse them
 public-coarsening: "SoTA portfolio" restores to the G.2 pack and, only when current, the exact C.18/C.19/G.5 continuation result

DPF-AUTHORING:
 intent: build a reusable FPF-grounded domain framework
 situation: a domain or local practice needs a reusable FPF-grounded framework edition rather than isolated advice
 question: is the useful first result a present organization-design proposal about an intended future framework, a settled framework-architecture decision, a post-claim architecture-description use, or a post-PFAD account of authoring dependencies?
 templateA: E.4.DPF Solution → FrameworkOrganizationDesignProposal@Context — before PFAD, when one current C.2.1 proposal episteme makes candidate organization claims reviewable; its EntityOfConcern is a present intended-framework-result description whose EntityOfConcern is an A.15.2 U.WorkPlan; proposal and description share the description's exact A.1-admitted grounding holon; its one ClaimGraph carries typed candidate claim nodes + proposed subject relation signatures; a relation-family coverage constraint node carries covered family ref-kind pairs + admitted use + coverage criterion; a WorkPlan acceptance target remains separate basis; a materialized PUA expectation expects this proposal, not the later framework edition; claim status carries proposedness; accountable obligation exits to A.2.8; a separate return points to E.4.PFAD when framework-architecture settlement is current; optional proposal meta-structure never substitutes for proposed subject organization
 templateB: E.4.PFAD Solution → PrincipleFrameworkArchitectureDecision@Context — when framework family / Core dependency boundary / content boundary / pattern relation structure / publication architecture / access architecture is the current decision question; the filled decision relation exists before any ADR-like publication of it
 templateC: C.30.AD Solution → ArchitectureDescriptionUseCard@Project — only after framework entity, ArchitectureOf@Context, and selected architecture-relevant structures exist, and when admissible use of the corresponding architecture description is current
 templateD: E.4.DPF Solution → FrameworkAuthoringDependencyDescription@Context — only when PFAD exists and immediate need is a minimal account of dependency availability and relevance for the next authoring use; this C.2.1 episteme concerns the current DPF-authoring U.WorkPlan, has one exact grounding holon, ClaimGraph, ReferenceScheme, and contains at least Core-edition, source-basis, PFAD dependency positions; Core edition + PFAD available with exact value-kind refs; another missing dependency has acquisition-condition description + no value ref; an available dependency has exact value+kind refs + no acquisition condition; relevance remains independent in both branches; future products need not exist; a missing PFAD returns to Template B
 stop: at the proposal while its candidate organization ClaimGraph is current; at PFAD while framework-architecture settlement is current; at the C.30.AD use card while post-claim description use is current; at the dependency description when it makes the next authoring work recoverable
 return: when intended result kind, current intended-result description, proposal basis, design question, candidate relation signature, constraint, invariant, dependency direction, alternative, unresolved position, Core edition, source basis, architecture decision, publication/access use, quality result, or currentness changes
 discipline: neither a topic list nor an organized proposal document without proposed subject relations is a proposal result
 public-coarsening: "DPF authoring" restores to FrameworkOrganizationDesignProposal@Context / PrincipleFrameworkArchitectureDecision@Context / ArchitectureDescriptionUseCard@Project / FrameworkAuthoringDependencyDescription@Context under the stated condition

SYSTEM-IN-CONTEXT:
 intent: make the current system question explicit
 situation: a candidate system is named, but the current system question is not yet explicit
 question: does the needed first result concern identity and environment, composition, participation and functioning, selected structures, intended creation/change, or creation/change that already occurred?
 templateA: A.1 Solution → HolonDelimitationRelation@Context — for identity rule, bounded context, included/excluded entities, environment relation, selected-structure boundary, or current boundary condition
 templateB: B.1.2 Solution → SystemAggregationRelation@Context — when aggregation depends on distinguishing admitted system parts from external crossing relations
 templateC: A.1 Solution → SystemParticipationRelation@Context — when current question connects the acting system to functioning, functional elements, roles, capabilities, methods, mechanisms, work plans, work occurrences, transformations, evidence, assurance, or temporal/dynamics aspects; each linked value keeps its direct governing pattern
 templateD: C.30 Solution → ArchitectureQuestionCard@Project — when system is identified and selected structures/architecture relations are now current
 templateE: A.15.2 Solution → U.WorkPlan — when planning intended system creation/change is current
 templateF: A.15.1 Solution → U.Work — only when creation/change/maintenance/other dated occurrence has happened and can be grounded through its performer, enacted method, affected referent, resources, outcome, time window, evidence relation; the occurrence is the direct result; ResultProducingWorkSlot[] remains absent; any planning/setup/authorization/causal relation to other work returns to its direct governor
 stop: at the smallest result that answers the current question
 return: when system identity, context, parthood, participation, selected-structure question, intended work, or performed-work evidence changes
 wrong-turn: restore system, environment, part, participation, architecture, plan, performed work, and description as separately governed values
 discipline: a diagram box is not a system boundary by shape; a functioning description is not the functioning system; a work record is not a system part merely because it appears inside one project view
 public-coarsening: "System in context" restores to the exact selected result under its selection condition
```
